# BLIS integration

The comparison runs BLIS v0.12.0 twice over matched single-turn workloads or multi-turn sessions. It models basic random routing and the upstream `inflight-load.yaml` llm-d configuration for combined instances or `pd.yaml` for separate pools. The browser replays recorded output; animation speed and pausing do not affect the simulation.

## Supported deployment

- Models: `llama-3.1-8b-instruct`, `qwen2.5-7b-instruct`, and `qwen3-14b`, using their BF16 checkpoint precision.
- Hardware: catalog `a100-80`, `h100`, and `h200`. All nine model/GPU pairs are supported.
- Allocation: 2–8 total GPUs, one GPU per replica; TP=1, PP=1, DP=1. Combined instances share one node. Separate pools use one GPU per node, with at least one prefill and one decode GPU.
- KV cache: `bfloat16`, block size 16, initially cold on both sides.
- Engine: vLLM 0.31.0 settings, context limit 32768, batch token budget 8192, maximum 256 sequences, GPU memory utilization 0.9.
- Router: no gateway latency or routing decision-time cost, no flow control. Optional prefill/decode disaggregation is described below.

These combinations execute in the pinned simulator. That establishes integration compatibility, not measured production accuracy for each deployment. The kernel's own coefficient provenance remains attached to the results. Model behavior such as thinking mode is not simulated; the user's configured token demands determine the workload.

Selector metadata is generated by `scripts/sync-deployments.py` into `cmd/server/deployments.json`. The generator verifies the catalog commit and reads checkpoint precision, native context limits, and GPU memory capacities from that checkout. The support list deliberately includes three models with sufficient native context for the common 32,768-token engine limit. Larger models requiring multiple GPUs per replica are not exposed.

GPU labels use the device family, while the memory hint shows the catalog's modeled capacity: 80.00 GiB for A100-80, 79.19 GiB for H100, and 139.80 GiB for H200. These are not substituted with the nominal marketing GB labels. The catalog comments distinguish vendor specifications, driver-reported values, and modeling assumptions.

The Go server embeds the snapshot and uses it for both selector metadata and validation. A comparison contains one shared configuration and resolved deployment metadata; both policy runs use it. Only router YAML differs. Changing a draft selection does not relabel an existing comparison. Model IDs, GPU IDs, and deployment metadata participate in the run cache key.

## Inputs and fairness

`blis.lock.json` pins the simulator, catalog, registry, and Go toolchain. The upstream simulator's Go module files pin its kernel, schema, and router dependencies. Setup verifies the downloaded source commits and the official Go archive checksum.

The default has 256 requests at 40 requests per second, mean 256 input tokens plus a 512-token shared prefix, mean 256 output tokens, and seed 42. Input and output lengths follow bounded Gaussian distributions with 25% standard deviation, minimum 16 tokens, and maximum twice the configured mean. Arrivals are Poisson. The presets are custom synthetic examples inspired by BLIS's catalog; their distributions are not claimed to be production traces or exact copies of catalog presets.

Both runs receive the same YAML and seed. Single-turn comparisons check every recorded arrival for identical request ID, timestamp, token counts, and SHA-256 hashes of the actual input/output token sequences. A missing request or content mismatch fails the comparison.

### Code generation

The code preset has 64 requests at 12 requests/second, mean 1,024 new input tokens plus a 2,048-token shared repository context, and mean 2,048 output tokens. Output length can reach 4,096 tokens under the bounded distribution. This models long decode phases; it does not execute code or measure generated-code quality.

### Multi-turn agents

The agent preset uses a BLIS cohort with one session per member (`single_session: true`), `closed_loop: true`, `context_growth: accumulate`, and independent prefixes (`prefix_sharing: per_member`). Defaults: 16 sessions, four turns, mean 256 new input and 256 output tokens per turn, 1,024 initial context tokens, 500 ms between turns, and 1,000 ms mean initial delay. Each session draws one exponential start delay; the cohort aggregate rate is `sessions × 1000 / meanStartMs` because BLIS divides it among the members. This is a finite population, not an imposed rate on follow-up requests.

A follow-up is generated only after the previous engine completion (combined instances) or parent completion callback (separate pools), plus the pause. Both policies share initial start times, session identity, token demands, and actual token content. Later arrivals may differ as a consequence of policy performance. BLIS follow-up request IDs include a completion-order counter; pairing uses `(sessionId, roundIndex)` while preserving the original IDs for raw metrics and routing traces. The service checks every turn's causal time and hashes the retained context to verify continuity.

**Pinned BLIS accumulation detail:** in v0.12.0, `SessionManager.OnComplete` retains `ProgressIndex - InputLen` output tokens, while completed-token metrics include the token sampled at prefill completion as well. For these uncapped sessions, retained output is one token shorter than generated output. The observer records that actual retention boundary at completion without changing BLIS behavior. `retainedOutputTokens`, `historyTokens`, `historyHash`, and `contextHash` make it explicit in the export; the inspector shows the actual retained context.

Supported agents have 1–64 sessions, 2–8 turns, pauses of 0–5,000 ms, and mean starts of 10–30,000 ms. Per-request simulation timeouts are disabled so a slower policy can finish its sessions; the API's wall-clock limit still applies. A conservative upper bound, `initialContext + 2 × turns × (newInputMean + outputMean)`, must fit the 32,768-token engine limit. This prevents truncation from changing token demands across policies. Tool execution, branching, reasoning quality, and context compaction are not modeled.

Exports include `fairness.mode` (`identical-arrivals` or `matched-sessions`), `matchedRequests`, and `identicalArrivalTimes`. The legacy `identicalInputs` field retains its stronger meaning of matched tokens **and** identical arrival times, so it can be false for a valid matched-session comparison.

The routing configurations are committed in `configs/`. Prefix caching and all engine settings are the same on both sides. The basic configuration is an explicit random-picker policy inside the embedded llm-d framework; it is not a measurement of an independently deployed proxy.

## Prefill/decode disaggregation

One shared `disaggregated` switch selects the layout for both policies. `instances` remains the total GPU budget. `prefillInstances` must be between 1 and `instances - 1`; the remaining instances form the decode pool. The server verifies recorded pool roles against this allocation before returning a comparison. Changing the budget clamps the draft split in the UI. Model, GPU, engine settings, workload, seed, pool allocation, and network remain identical across policies.

Disaggregated scenarios use `cluster.nodes = instances`, `gpus_per_node = 1`, explicit prefill/decode deployment pools, and `NixlConnector`. The catalog provides `ib-400g` (50 GB/s), `roce-200g` (25 GB/s), and `ethernet-100gbe` (12.5 GB/s) nominal inter-node bandwidth. `--pd-transfer-contention` enables BLIS's shared-link contention model. These are catalog specifications, not a claim of measured network performance.

`basic-pd-router.yaml` filters by pool role and picks randomly within each pool. `llmd-pd-router.yaml` follows the pinned upstream `pd.yaml`: approximate prefix-cache score with weight 2, queue score with weight 1, and max-score selection. Both use `always-disagg-pd-decider` and `disagg-profile-handler`. This isolates routing within matched separate pools; asymmetric layouts are outside this comparison mode.

The adapter reads `ParentRequests()` and `PoolMembership()` after execution. Explicit child IDs join prefill/decode events to original requests, preserving session/turn metadata. Prefill child completion only means input KV is ready. Its streaming marker is discarded. Decode queue entry uses the parent's recorded `DecodeEnqueueTime` because that engine path bypasses the ordinary queue hook. First-token timing comes from BLIS's projected parent TTFT. Completion comes from parent `CompletionTime`, including the fixed post-decode overhead used by its session callback; full client latency still comes from BLIS metrics, which can include further output-processing overhead.

Transfers export the prefill completion, actual start/end, standalone duration, total/pulled KV blocks, child IDs, and both instance IDs. The interval before transfer starts represents waiting for decode KV capacity. Transfer duration includes modeled link contention; the aggregate contention delay is BLIS's actual transfer duration minus its standalone cost. Decode prefix reuse reduces the blocks pulled. The browser does not stretch or invent transfer times; **Inspect next transfer** pauses at a transfer's midpoint. Raw engine child events and raw `KVTransfers`/routing records remain in the export.

Live received/finished counts use normalized parent events, never the sum of both pools' child completion counters. KV occupancy uses the original snapshots. The retained-context observer also covers the PD parent session callback, preserving causal follow-up arrival checks even with zero pause.

## Recorded playback

The adapter adds a value-only observer to the pinned source. Its patch anchors and added files are committed in `scripts/build-blis.py` and `integrations/blis/`. The observer is enabled only by `BLIS_PLAYBACK_PATH` and neither changes simulation state nor consumes random values.

| Event | Source |
|---|---|
| Arrived | Existing cluster arrival hook |
| Routed / preparing input | Existing routing decision trace and its timestamp |
| Queued | Engine QueuedEvent after enqueue |
| Processing | Engine ScheduledEvent |
| Streaming | Recorded first-token time when the first token is produced |
| Finished | Engine RequestLeftEvent |
| Queued again | Batch formation's preemption transition |
| Timed out | Engine timeout transition |

The exported first-token event uses the timestamp already calculated by BLIS. It can be recorded before simulation time reaches that timestamp; the exporter sorts events by their timestamps. Arrival and routing precede endpoint events when timestamps tie. Other equal-time ordering is preserved for combined instances. PD ties follow the parent lifecycle: arrival, routing, prefill queue/work, KV capacity wait, transfer start/end, decode queue/work, first token, and terminal outcome.

The “Preparing input” interval is distinct from engine queue wait. Queue wait is calculated from recorded queue-entry and scheduling intervals, including preemption. BLIS's `scheduling_delay_ms` is retained in raw metrics but is not substituted for this interval.

For combined instances, the Finished event is the engine's departure time. Client response timing may include additional output-processing or completion overhead. The full-run latency table uses BLIS's metrics rather than deriving latency from the engine completion marker.

Progress snapshots are sampled at approximately 50 ms intervals of simulated time using BLIS's `ProgressHook`. The UI shows the most recent available snapshot at or before the playback cursor, never a future sample. KV occupancy is modeled cache occupancy, not measured GPU utilization. Request states and live counts come from recorded lifecycle events. Up to 30 squares per instance are shown, with an explicit overflow count; all requests remain searchable.

## Latency target assessment

`src/analysis.ts` evaluates a completed comparison in the browser; targets do not modify BLIS configuration, cache keys, or simulation behavior. Defaults of 1,000 ms TTFT, 10,000 ms full response, and 95% joint coverage are editable examples. Limits are inclusive. The numerator includes only parent requests with a completed lifecycle and finite nonnegative BLIS `ttft_ms` and `e2e_ms`, where both limits hold on that same request. The denominator is the maximum of planned requests, injected requests, and observed parent arrivals. Failed, unfinished, missing-measurement, and un-emitted planned agent turns therefore cannot inflate the pass rate. Agent requirements are per call, not per session. The verdict compares unrounded counts against the required percentage.

Explanation populations are separate from target populations: match valid completed requests by request ID, or session/turn for agents. Use the same pairs to compare mean TTFT and response time. Phase explanations additionally require consistent queue and transfer records on both sides. Report excluded timelines explicitly instead of fabricating contributions. Averages are additive; differences of percentiles are not decomposed as phase costs.

The first-token path is partitioned into arrival-to-first-engine-queue preparation (including endpoint rendering/tokenization and admission waiting), recorded engine/prefill/decode queue intervals clipped at the first-token boundary, decode KV-space wait, standalone KV transfer cost, additional transfer contention, and a residual for prompt processing plus first-token overhead. The interval after first token is BLIS E2E minus TTFT and includes later queueing, output generation, and output-processing overhead. Preemptions open new queue intervals; duplicate queue markers do not reset waits. Transfer contention is actual transfer duration minus standalone duration and is counted only once. Their sum equals mean BLIS E2E on the explained population.

Queue findings choose the instance/queue role with the most accumulated wait before first token and report its population and mean wait, including zero waits among the matched requests assigned there. Links select the actual parent/session turn with the largest absolute paired phase difference and pause on the slower side's recorded interval; both policy clocks remain synchronized. These are observed differences, not counterfactual route predictions or causal estimates of an isolated setting change.

JSON exports add `assessment` with schema version 1, active targets, both target scorecards, paired populations, mean deltas, phase comparisons, request evidence, and queue findings. Raw BLIS data remains intact. Invalid target entries hide the verdict and disable export until corrected.

## Metrics and provenance

BLIS internal event clocks are microseconds. The UI converts them to seconds for playback and milliseconds for request durations. Per-request and aggregate latency fields in BLIS's metrics JSON are already milliseconds.

The latency table uses the completed-request aggregates from the metrics file. Agent session p95 is the nearest-rank percentile of each completed session’s final client-visible response minus its first arrival, including inter-turn pauses. It reports failed and unfinished counts alongside them. Throughput divides completed output tokens by a common window from time zero to the later end of the two runs, including recorded client-visible response timing. It does not compare two different throughput denominators or silently use stdout aggregates.

Full-run metrics are labeled and remain fixed during playback. The inspector marks future lifecycle events as upcoming; its final timing and score details are explicitly recorded full-run information.

Each run directory retains the common workload, scenario, router YAML, executed arguments, BLIS log, metrics, TraceV2 export, and playback export. The comparison cache key includes configuration, dependency pins, adapter version, router configurations, adapter source, and comparison-service source. Only a successful complete comparison is cached.

## Current boundary

The simulator covers chat, summarization, code generation, and multi-turn agents on the nine supported deployments. Additional GPUs/models, multi-GPU replicas, burstiness controls, asymmetric pool layouts, capacity sweeps, and session-level latency targets remain later milestones. It runs as a local development tool; hosted multi-user execution and deployment automation are not implemented.
